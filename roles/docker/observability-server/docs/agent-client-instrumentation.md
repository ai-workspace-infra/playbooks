# ChatGPT App and Claude Code telemetry boundary

This stack accepts OTLP/HTTP at `https://observability.svc.plus/otlp/v1/{traces,metrics,logs}` and forwards it to the in-stack collector.  It is designed for telemetry generated by software that your team controls; never send prompts, source code, credentials, or raw tool arguments as metric labels.

## ChatGPT App

ChatGPT is a hosted client, so its model runtime cannot be wrapped with the OpenLIT SDK.  A custom ChatGPT App/MCP connector can observe **the remote MCP service that you operate**, not the private ChatGPT model turn, model tokens, or the internal tool-selection trace.

Instrument the remote MCP server (or an API/gateway called by that server) with OpenLIT.  Give it stable resource attributes such as `service.name=chatgpt-mcp-gateway`, `agent.name=chatgpt`, `agent.type=chat-agent`, and `deployment.environment.name=uat`.  Emit a span around each MCP tool request and propagate the trace context to downstream HTTP, database, and queue calls.  Capture only safe business metadata; hash user identifiers and omit the prompt and tool arguments by default.

For Business and Enterprise/Edu, ChatGPT custom apps connect to **remote** MCP servers.  A local collector is therefore not a valid direct endpoint unless it is securely tunneled or otherwise exposed as an approved remote service.  Conversation-level governance/audit needs to come from the workspace's approved compliance workflow, not from OpenLIT injected into the ChatGPT desktop/web app.

## Claude Code

Do not run `openlit-instrument claude` and assume it instruments Claude Code itself.  OpenLIT supports applications using the Anthropic Python/TypeScript SDK; Claude Code is a separately packaged client and its hosted-subscription traffic is not an OpenLIT SDK integration point.

Use one of these supported boundaries instead:

1. **Preferred for Claude Code model usage:** route Claude Code through the existing LiteLLM/LLM gateway using Anthropic's documented `ANTHROPIC_BASE_URL` and authentication settings.  The gateway becomes the authoritative source for model request count, tokens, cost, model and provider.  Instrument the gateway with OpenLIT or native OpenTelemetry and export OTLP to this collector.
2. **For MCP/tool operations:** instrument each MCP server process you own with OpenLIT/native OpenTelemetry.  Create server spans for tools, annotate only the approved attributes (`tool.name`, `mcp.server.name`, outcome and duration), and forward the trace context to infrastructure calls.
3. **For agents you build with the Anthropic SDK:** use OpenLIT directly.  For example, set `OTEL_SERVICE_NAME`, `OTEL_DEPLOYMENT_ENVIRONMENT`, and `OTEL_EXPORTER_OTLP_ENDPOINT`, then invoke `openlit-instrument` for that application process.  This provides LLM, token, cost, tool and framework telemetry without modifying business code.

## Common OpenLIT environment

```sh
export OTEL_SERVICE_NAME='xworkmate-agent'
export OTEL_DEPLOYMENT_ENVIRONMENT='uat'
export OTEL_EXPORTER_OTLP_PROTOCOL='http/protobuf'
export OTEL_EXPORTER_OTLP_ENDPOINT='https://observability.svc.plus/otlp'
export OTEL_RESOURCE_ATTRIBUTES='agent.name=xworkmate,agent.type=coding-agent,workspace.id=xwork,gen_ai.provider.name=anthropic'
openlit-instrument python app.py
```

For an OpenLIT TypeScript/Python SDK integration, set the same endpoint and resource attributes in `openlit.init(...)`.  The collector derives `env` from `deployment.environment.name`, exports traces to VictoriaTraces, logs to VictoriaLogs, received application metrics to VictoriaMetrics, and creates span-derived RED metrics for every instrumented service.

## Dashboard expectations

The Agent / AI Application Observability dashboard becomes useful as soon as traces arrive: active agents, run rate, error rate, latency, tool calls, MCP calls and service distribution are computed by the collector.  Token, cached-token and cost panels require the gateway or SDK to emit their corresponding OTLP GenAI metrics.  Logs containing `trace_id` get a VictoriaLogs-to-VictoriaTraces link; metrics carry trace exemplar destinations where the emitting SDK supplies exemplars.
