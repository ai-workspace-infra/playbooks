# Dev feature Flux owner

Reuses the established single-host Playbooks execution pattern and existing Dev
SSH binding. This is a separate capability from the production-only root Source
promotion role; it never changes that role, the Dev platform Source, or a global
root to point at a feature branch.

The controller validates a full GitOps SHA, builds only the fixed component lane
path with builtin Kustomize and rejects generators/remote files, Secret values,
RBAC, nested Flux Sources and cluster resources. Four fixed ConfigMaps, the
reviewed immutable chart, six component image digests, scoped Helm identity and
exact onwalk.net Ingress hosts are required. Namespaced Role/RoleBinding and
lane-reconciler ServiceAccount are generated by trusted owner code, not PR
manifests. Namespace Pod Security is restricted at v1.37. No role wildcard,
clusterrole, exec/proxy/token-subresource, or role-binding permission is granted.

Modes are explicit: plan (read-only Kubernetes observations), prepare (only
namespace/limited identity plus exact registry), submit (HTTP source, pending), verify (read-only seeded readiness), enable-tls (only the
fixed TLS sub-Kustomization, after real DNS A/HTTP entrypoint checks). A prepare
result is not deployment verification. Neither the owner nor tests fabricate
application Secrets or TLS certificates. Pruning is disabled; cleanup needs its
own authorization and must preserve independent UAT/data.

SIT uses feature-xconnect-referral-sit and a fixed PR commit. Dev K3s accepts
only SIT; persistent UAT is delivered by its separate Serverless owner.
The controller uses the namespace-bound lane-reconciler identity.

Inputs dev_feature_config/report are produced by the trusted adapter, not passed
from an arbitrary PR. node/cluster UIDs and protected platform revision must
match real runtime state before and after writes. Existing namespaces with a
different owner are rejected. Readiness requires source, namespace Kustomization
and HelmRelease at the observed revision; business, database identity, Stripe
Sandbox and external TLS acceptance remain separate.

Required namespace app credentials/database admin/runtime identities are owned
by their existing secret/data owner; TLS uses the separately reviewed Traefik
ACME resolver and no copied Secret. Platform Traefik, DNS and public firewall
changes are distinct infrastructure owner operations. This workflow never reads
production or shared application Secret values and adds no Vault permission.

`prepare` creates only the fixed namespace/SA/Role/RoleBinding, then invokes the existing `vhosts/k3s_runtime_secret_sync` opt-in Dev registry mode. This reads only `kv/CICD/dev/ghcr` and writes only `web-saas-registry` in the selected fixed lane. The default KV field-sync mode remains unchanged. Secret values stay in controller memory and strict SSH stdin; no artifact contains them.

`verify` requires a same-run authenticated `dev-lane-seed/v1` receipt artifact and digest from a separately reviewed seed producer. It must bind candidate_sha, namespace, instance 109277144, node UID and cluster UID, result=verified, schema_initialized=true and database_roles=[xc_accounts_rw,xc_billing_rw]. This interface does not implement schema initialization or accept a caller boolean. The Toolkit caller must verify the artifact producer source/run before passing it. No seed producer exists in this PR: final runtime verification remains blocked until that owner is implemented. In particular PG readiness/DDL/DB-role preparation must precede full HelmRelease readiness; business must not receive lane_admin.

SIT is a fixed commit. UAT releases use the separate Serverless pipeline. TLS is a separate exact `/tls` path, enabled only after all three fixed onwalk.net hosts resolve uniquely to the Dev IP and HTTP port 80 responds without redirects. Traefik ACME `dev-http01` owns certificates; no namespace TLS Secret is copied. Platform Traefik resources require a separate reviewed infrastructure owner and are rejected by this feature renderer.

Proposed Vault changes (NOT applied): retain bootstrap e460 claim; add the reviewed new Playbooks `dev-feature-flux.yml@<final full SHA>` callee with Toolkit main-only `.github/workflows/dev-feature-deploy.yml@refs/heads/main` caller and environment dev, and add read only `kv/data/CICD/dev/ghcr` to the exact existing Dev role. Keep existing exact `kv/data/CICD/dev/k3s-bootstrap` read; no cloudflare, PROD, wildcard path, secret write or GitHub Secret fallback. Caller infrastructure workflow must merge to main before OIDC authorization. Business SIT candidate remains an unmerged fixed PR commit.

Ordered handoff: prepare namespace+registry → B seed DB-admin only → submit fixed Flux controllers (returns submitted_pending_seed, never PASS) → B wait PG then initialize schema/roles/runtime Secrets → verify six-component readiness with B seed receipt. verify performs no object apply. This breaks the PG/full-Helm readiness dependency cycle.

Candidate evolution does not change this execution owner or its Vault callee claim. `gitops_sha` is fixed for one run, not permanently fixed to PR605. The protected Toolkit main caller resolves the actual PR using GitHub API, verifies same repository/main baseline/current head/ancestry/CI plus build provenance, and uploads a same-run `receipt.json` artifact. It supplies artifact name + SHA256 as `candidate_artifact`/`candidate_sha256`. The owner verifies digest, current run binding, exact checkout HEAD and constrained manifests; it never treats a raw workflow input JSON or a PR-authored receipt as approval.

Candidate receipt v1 fields: `schema_version=dev-feature-candidate/v1`, `result=verified`, `repository=ai-workspace-infra/gitops`, `stage`, positive integer `candidate_pr`, full `candidate_head` matching gitops_sha, `base_ref=main`, full `base_sha`, `checks=success`, `same_repository=true`, `main_ancestry_verified=true`, and `source={workflow_ref: ai-workspace-infra/platform-ops-toolkit/.github/workflows/dev-feature-deploy.yml@refs/heads/main, run_id: <current run>}`. These are public API-verification results from the trusted producer, not self-certified arbitrary caller input. Caller must verify the real producer before invoking this owner. Component image repositories stay allowlisted and digests may evolve; source repository/SHA, build-run and image-digest annotations and workload IMAGE must agree. Actual release/build provenance is verified by the caller.
